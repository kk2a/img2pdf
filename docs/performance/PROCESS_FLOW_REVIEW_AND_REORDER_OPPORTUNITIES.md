# ImageToPdf 処理フローレビューと高速化候補

作成日: 2026-04-11  
対象ブランチ: enhance/speed

## 1. 目的

現行実装の処理順を明文化し、以下を点検する。

- 重複している処理がないか
- 並び替えで待ち時間や無駄メモリを減らせないか
- 小さい変更で段階導入できるか

本資料は、直近のコード状態を前提にした技術メモである。

## 2. 現行の処理フロー

### 2.1 エントリポイント

1. main が rayon のグローバルスレッドプールを初期化する
2. 引数ありなら CLI モード、引数不足なら GUI モード
3. CLI モードでは実行時間計測を開始し、終了時に実行時間を表示する

### 2.2 CLI モード開始

1. 入力フォルダから JPEG を収集
2. ファイル名でソートして処理順を固定
3. 進捗チャネルと完了チャネルを作成
4. 進捗表示スレッドを起動
5. ImageProcessor::run を呼び出し、処理スレッド側で本処理を実行

### 2.3 画像処理フェーズ (並列)

各ファイルに対して並列で以下を実行する。

1. 画像読込
2. RGB8 へ変換
3. A4 比率に収まるようにリサイズ
4. JPEG エンコード
5. jpegtran があれば可逆最適化を試行
6. 処理完了カウントを AtomicUsize で更新
7. 進捗は整数パーセント変化時のみ通知

補足:
- 白キャンバス合成は廃止済みで、リサイズ後画像をそのまま JPEG 化している

### 2.4 集約フェーズ (単一スレッド)

1. 結果を index でソートして入力順を回復
2. 成功ページとエラーを分離
3. 成功が 0 件なら失敗終了
4. Saving フェーズの進捗通知を送信

### 2.5 PDF 生成フェーズ (単一スレッド)

1. pdf-writer で PDF を構築
2. ページ、画像XObject、コンテンツストリームの各オブジェクトを作成
3. 画像を A4 上でアスペクト比維持の中央配置
4. バイト列をファイルに書き込み

## 3. 重複処理の点検結果

### 3.1 解消済み

- 白キャンバス生成 + overlay 後の JPEG 化
  - 以前はページ全面バッファを毎枚生成していたが、現在は廃止済み
  - 効果: メモリ確保・塗りつぶし・コピーの削減

### 3.2 現在も残る重複/余地

- JPEG 最適化で毎回 temp ファイル作成/削除
  - 画像枚数分だけ create/write/read/delete が発生
- JPEG 読込直後に全画像を RGB8 化
  - 入力が既に JPEG の場合でも decode -> RGB -> re-encode は必須設計
  - 品質/要件上やむを得ないが、コストは高い
- 進捗通知の算出が各タスク完了時に毎回実施
  - 軽量だが、枚数が非常に多いと無視できない

## 4. 並び替えで改善できる可能性

## 4.1 候補A: 重い画像を先に処理する順序へ変更

現状:
- 事前にファイルサイズを取得し、大きい順で並列投入済み

実装:
- 事前にファイルサイズを取得し、大きい順で並列投入する
- 出力順は既存どおり index ソートで元順回復する

狙い:
- tail latency の圧縮
- 終盤で重い画像だけ残る現象を軽減

リスク:
- 事前の metadata 取得コストが増える
- 効果はデータセット依存

優先度:
- 採用済み

## 4.2 候補B: 進捗通知を count ベース固定間隔へ変更

現状:
- パーセント変化時のみ通知

提案:
- min(1%, 16枚, 50ms) のような二重条件で送信

狙い:
- 小枚数時の飛び飛び表示を緩和
- 通知頻度を上限管理して CPU 側の阻害を抑える

リスク:
- UX と速度のトレードオフ調整が必要

優先度:
- 高 (A-3)

## 4.3 候補C: jpegtran をフェーズ分離してバッチ化

現状:
- 並列タスク内で jpegtran を即時実行

提案:
- まず JPEG エンコードのみ完了
- その後、別フェーズで jpegtran を並列バッチ処理

狙い:
- CPU バウンド処理と外部プロセス/I-O 処理の競合を緩和

リスク:
- 実装が複雑化
- 一時データ管理が増える

優先度:
- 中

## 4.4 候補D: パイプライン化 (読込/変換 と PDF 書込の重畳)

現状:
- 全ページの JPEG が揃ってから PDF 生成

提案:
- チャネル経由でページを逐次渡し、PDF 側は受信しながら書き込み

狙い:
- メモリピーク削減
- 終端待ちの短縮余地

リスク:
- page tree/object ID の管理を再設計する必要
- 変更規模が大きい

優先度:
- 低 (将来検討)

## 5. 今回時点の所見

- 現行は、不要な白キャンバス合成を除去済みで、処理重複は既に一段減っている
- 直近で最も安全に効きやすいのは、以下2点
  - A-3: 進捗通知ルールの時刻/件数ベース化
  - B-2: jpegtran 実行パスのI/O削減 (失敗時フォールバックも含む)
- 並び替え施策としては、重い画像先行投入が小変更で試しやすい

## 6. 次の実験提案 (小さい差分順)

1. 施策ID A-3
   - 進捗通知を件数+時刻の二重条件で間引く
2. 施策ID B-2-1
   - jpegtran 失敗時の早期リターン最適化と temp I/O 回数点検
3. 施策ID B-2-2
   - 入力ファイルサイズ降順投入を比較実験として追加
