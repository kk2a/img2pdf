# 問題点とパフォーマンス改善

## 修正した問題

### GUI 下部の余白が大きい
- 原因: ウィンドウ高さが実際のウィジェット配置より大きく、進捗セクション下に余白が残っていた。
- 対応: `WINDOW_HEIGHT` を 530px から 430px に縮小し、下端の余白を自然なサイズにした。

### 入力フォルダ選択と出力先選択のダイアログが別 UI
- 原因: 入力フォルダは `dir_chooser`、出力先は `NativeFileChooser` を使っていた。
- 対応: 入力フォルダも `NativeFileChooserType::BrowseDir` に統一した。最後に使った入力フォルダも設定に保存する。

### `apt-get install libjpeg-progs` の jpegtran が見つからない
- 原因: `tools/jpegtran(.exe)` だけを探しており、Linux の `/usr/bin/jpegtran` など PATH 上の実行ファイルを見ていなかった。
- 対応: 探索順を `tools/` → プロジェクト直下 → PATH に拡張した。これで `libjpeg-progs` の jpegtran を利用できる。

### テストの CLI 仕様不一致
- 原因: 実装では入力フォルダだけでも既定の PDF 名を生成するが、テストは `None` を期待していた。
- 対応: テストを現行仕様に合わせ、既定出力名が生成されることを確認する内容に修正した。

## 実装したパフォーマンス改善

### jpegtran の一時ファイル I/O 削減
- 以前: JPEG ごとに一時入力ファイルと一時出力ファイルを書き出して jpegtran を実行。
- 現在: stdin/stdout パイプで jpegtran と JPEG バイト列を直接受け渡す。
- 効果: ディスク I/O と一時ファイル削除処理を削減し、特に枚数が多い場合の実行速度を改善する。ファイルサイズ最適化は従来通り `-copy none -optimize` で維持。

## 今後検討できる改善

- jpegtran プロセス起動は画像ごとに発生するため、小さい画像が非常に多い場合は起動コストが目立つ可能性がある。
- PDF 生成前に全ページの JPEG をメモリへ保持するため、巨大な画像セットではメモリ使用量が増える。ストリーミング生成やバッチ書き出しが検討候補。
- GUI のキャンバス幅変更検知はイベントループでポーリングしているため、入力ウィジェットのコールバック化で無駄なチェックを減らせる。
